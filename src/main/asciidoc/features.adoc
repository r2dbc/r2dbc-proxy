== Accessing Reactor Context Values

In the callbacks, `ValueSource` contains a Reactor `ContextView` object under the `ContextView.class` key.
This provides read-only access to the Reactor context.

[source,java]
----
@Override
public void beforeQuery(QueryExecutionInfo execInfo) {
    // query execution scoped context
    ContextView contextViewForQuery = execInfo.getValueStore().get(ContextView.class, ContextView.class);
    // connection scoped context
    ContextView contextViewForConnection = execInfo.getConnectionInfo().getValueStore().get(ContextView.class, ContextView.class);
    // ...
}
----

=== Available `ContextView` scopes

As you interact with R2DBC APIs, values may be written to Reactor contexts in several places. The following
example shows which context values are available in the corresponding callback APIs.

[source,java]
----
Mono.from(connectionFactory.create()).contextWrite(context -> context.put("foo", "FOO"))   // <1>
    .flatMapMany(connection -> Mono.from(connection
        .createStatement("SELECT id, name FROM emp WHERE id = ?")
        .bind(0, 20)
        .execute()).contextWrite(context -> context.put("bar", "BAR")))    // <2>
    .flatMap(result -> Mono.from(result
        .map((row, rowMetadata) -> row.get("name", String.class)))
        .contextWrite(context -> context.put("qux", "QUX"))    // <3>
    )
    .contextWrite(context -> context.put("baz", "BAZ"))    // <4>
    ...
----

<1>  Context for the connection
<2>  Context for query execution
<3>  Context for result-set retrieval
<4>  Context for the entire flow

*BindParameterConverter#onCreateStatement*

* `StatementInfo#getValueStore` has no `ContextView`
* `ConnectionInfo#getValueStore` has a `ContextView` containing keys `foo` and `baz`

*BindParameterConverter#onBind*

* `StatementInfo#getValueStore` has no `ContextView`
* `ConnectionInfo#getValueStore` has a `ContextView` containing keys `foo` and `baz`

*ProxyExecutionListener#[before|after]Query*

* `QueryExecutionInfo#getValueStore` has a `ContextView` containing keys `bar` and `baz`
* `ConnectionInfo#getValueStore` has a `ContextView` containing keys `foo` and `baz`

*ProxyExecutionListener#[before|after]Method*

* `MethodExecutionInfo#getValueStore` for `create` has a `ContextView` containing keys `foo` and `baz`
* `MethodExecutionInfo#getValueStore` for `createStatement` has no `ContextView`
* `MethodExecutionInfo#getValueStore` for `bind` has no `ContextView`
* `MethodExecutionInfo#getValueStore` for `execute` has a `ContextView` containing keys `bar` and `baz`
* `MethodExecutionInfo#getValueStore` for `map` has a `ContextView` containing keys `baz` and `qux`
* `MethodExecutionInfo#getValueStore` for `get` has no `ContextView`
* `ConnectionInfo#getValueStore` for all methods (`create`, `createStatement`, `bind`, `execute`, `map`, `get`) has a `ContextView` containing keys `foo` and `baz`

[[features_micrometer-observation-support]]
== Micrometer Observation Support

R2DBC Proxy has an optional dependency on Micrometer to provide https://micrometer.io/docs/observation[Micrometer Observation] support.
The `ObservationProxyExecutionListener` creates observations for query execution.

.Configuration sample
[source,java]
----
ConnectionFactory connectionFactory = ...
ObservationRegistry observationRegistry = ...
String r2dbcUrl = ...

ObservationProxyExecutionListener listener = new ObservationProxyExecutionListener(
observationRegistry, connectionFactory, r2dbcUrl);
listener.setIncludeParameterValues(true);  // include binding params (default is false)

ConnectionFactory proxyConnectionFactory = ProxyConnectionFactory.builder(connectionFactory)
    .listener(listener)
    .build();
----

All https://micrometer.io/docs/observation[Micrometer Observation] implementation classes live in the
`io.r2dbc.proxy.observation` package. Because this dependency is optional, users must explicitly add the
`micrometer-observation` dependency.

For Spring Boot 3, a separate project, _TBD_, provides auto-configuration.

[IMPORTANT]
.Virtual Thread Environment
====
The default `QueryObservationConvention` includes the thread name as a low-cardinality tag in spans.

In a virtual-thread environment, each thread has a unique name. As a result, tagging thread names as a
low-cardinality key-value pair can lead to cardinality explosion in tracing backends.

To avoid this, use `VirtualThreadQueryObservationConvention`, a subclass of `QueryObservationConvention`,
which omits the thread-name tag. This convention is recommended when running in a virtual-thread environment.
====
